    C++20 — what you write

    // producer: write payload, then release tail_
storage_[tail & kMask] = item;
tail_.store(tail + 1, std::memory_order_release);

// consumer: acquire tail_, then read payload
const auto tail = tail_.load(std::memory_order_acquire);
out = storage_[head & kMask];
head_.store(head + 1, std::memory_order_release);

    The release store orders the slot write before the index write. The acquire load orders the index read before the slot read. Paired, they guarantee the consumer never sees the new tail without the new data.

    Real generated assembly

    ; ARM64 — verbatim clang++ -O2 -S output of try_push (Apple Silicon)
ldr   x8, [x9]                  ; tail_.load(relaxed)
ldapr x10, [x10]                ; head_.load(acquire) — REAL instr
str   w0, [x10, x9, lsl #2]     ; storage_[tail & 7] = v
stlr  x8, [x9]                  ; tail_.store(release) — REAL instr

; x86-64 — the same atomics compile to plain mov (x86 TSO already
; guarantees the ordering; reproduce: clang++ -O2 -S -masm=intel)
mov   DWORD PTR [rcx+rdx], esi  ; payload write
mov   QWORD PTR [rdi+0x40], rdx ; tail_.store(release) — no lock, no fence

    On ARM64 the ordering is literally visible in the instruction stream (ldapr = load-acquire, stlr = store-release). On x86-64 the same code is plain mov — the hardware memory model gives acquire/release semantics for free. Either way: zero locks, zero fences, zero CAS loops. That's why this queue is cheap.
